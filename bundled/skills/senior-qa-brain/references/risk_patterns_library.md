# 风险模式库（实用性优先版）

> 聚焦高频高风险场景，排除理论极端场景

## ⚠️ 实用性原则

- ✅ 只包含**真实发生过**的高频风险
- ✅ 测试方法**简化实用**，不追求完美覆盖
- ❌ 排除**理论风险**但实际很少发生的场景
- ❌ 排除**需要专业安全团队**才能测试的高级攻击

## 风险识别矩阵

| 功能类型 | 常见风险 | 风险等级 | 历史Bug频率 |
|---------|---------|---------|------------|
| 用户认证 | 会话劫持/越权 | 🔴 高 | ⭐⭐⭐⭐⭐ |
| 支付流程 | 金额篡改/重复支付 | 🔴 高 | ⭐⭐⭐⭐⭐ |
| 文件上传 | 恶意文件/路径穿越 | 🔴 高 | ⭐⭐⭐⭐ |
| 表单提交 | SQL注入/XSS | 🔴 高 | ⭐⭐⭐⭐ |
| 数据展示 | XSS/数据泄露 | 🟠 中 | ⭐⭐⭐ |
| 搜索功能 | 性能/注入 | 🟠 中 | ⭐⭐⭐ |
| 评论系统 | XSS/垃圾内容 | 🟠 中 | ⭐⭐⭐ |
| 分页列表 | SQL注入/性能 | 🟡 低 | ⭐⭐ |
| 主题切换 | 样式冲突 | 🟢 极低 | ⭐ |

## 一、安全风险模式

### 1.1 SQL注入 (SQL Injection)

#### 风险场景识别
```
✅ 有SQL注入风险的场景:
- 用户输入直接拼接到SQL语句
- 搜索功能的keyword参数
- 筛选条件的动态查询
- 排序字段的动态指定
- 登录/注册的邮箱/用户名输入
```

#### 攻击向量库（实用版 - 只测1-2个）⭐
```sql
✅ ' OR '1'='1  （基础注入，必测）
✅ admin'--      （注释绕过，可选）

❌ 不测以下高级攻击（除非是安全敏感系统）：
   - UNION SELECT查询
   - 时间盲注
   - 布尔盲注
   - 堆叠查询
   - 宽字节注入
```

#### 测试用例模板（简化版）
```
TC_SQL_001: 在【字段名】输入 ' OR '1'='1 ，验证是否被过滤

可选（P2优先级）：
TC_SQL_002: 在【字段名】输入 admin'-- ，验证是否被拦截

❌ 不推荐：
   - URL编码绕过测试
   - 时间盲注测试
   - 其他高级SQL注入变体
```

**理由**：如果基础payload被拦截，说明防护有效；如果基础payload通过了，高级payload也会通过。

**历史案例**: 登录页SQL注入、搜索功能注入导致数据删除

---

### 1.2 跨站脚本攻击 (XSS)

#### 风险场景识别
```
✅ 有XSS风险的场景:
- 用户输入会展示给其他用户（评论、昵称、简介）
- 富文本编辑器内容展示
- URL参数直接显示在页面
- 错误信息包含用户输入
- 搜索结果显示搜索关键词
```

#### 攻击向量库（实用版 - 只测1个）⭐
```html
✅ <script>alert('XSS')</script>  （基础XSS，必测）

❌ 不测以下高级攻击（除非是安全敏感系统）：
   - <img src=x onerror=alert('XSS')>
   - 编码绕过（URL编码、Base64）
   - DOM型XSS复杂利用
   - SVG注入
   - CSS注入
```

#### 测试用例模板（简化版）
```
TC_XSS_001: 在【字段名】输入 <script>alert('XSS')</script> ，验证是否被转义

❌ 不推荐：
   - 多种XSS变体测试
   - 编码绕过测试
   - 复杂的DOM型XSS测试
```

**理由**：基础<script>标签是最常见的XSS攻击，如果这个被拦截，说明有基础防护。

**历史案例**: 用户昵称XSS、搜索结果XSS导致Cookie泄露

---

### 1.3 跨站请求伪造 (CSRF)

#### 风险场景识别
```
✅ 有CSRF风险的场景:
- 敏感操作没有二次确认（修改密码、转账）
- 没有CSRF Token验证
- 使用GET请求执行修改操作
- Cookie-based认证且没有SameSite设置
```

#### 攻击示例
```html
<!-- 恶意网站的代码 -->
<form action="https://bank.com/transfer" method="POST" id="csrf-form">
  <input type="hidden" name="to" value="attacker">
  <input type="hidden" name="amount" value="10000">
</form>
<script>
  document.getElementById('csrf-form').submit();
</script>
```

#### 测试用例模板（简化版）
```
TC_CSRF_001: 不带CSRF Token提交表单，验证是否被拦截

可选（P2优先级）：
TC_CSRF_002: 使用过期的CSRF Token提交，验证是否失效

❌ 不推荐：
   - Cookie的SameSite属性详细测试
   - 复杂的CORS策略测试
```

**理由**：基础CSRF防护测试足够，复杂场景应该由安全团队负责。

### 1.4 权限与越权 (Authorization)

#### 横向越权 (Horizontal Privilege Escalation)

**风险场景**:
```
用户A访问用户B的数据
- 修改URL参数 /user/123 改为 /user/456
- 修改接口参数 {userId: 123} 改为 {userId: 456}
- Cookie篡改
```

**测试用例模板**:
```
TC_AUTH_H_001: 用户A访问 /api/user/B/profile ，验证403
TC_AUTH_H_002: 用户A修改订单 {orderId: B_order} ，验证403
TC_AUTH_H_003: 用户A删除 userB 的内容，验证403
TC_AUTH_H_004: 使用代理工具篡改请求中的userId，验证后端校验
```

#### 纵向越权 (Vertical Privilege Escalation)

**风险场景**:
```
普通用户访问管理员功能
- 直接访问管理后台URL
- 调用管理员API
- 猜测管理员路径
```

**测试用例模板**:
```
TC_AUTH_V_001: 普通用户访问 /admin ，验证403或重定向
TC_AUTH_V_002: 普通用户调用 POST /api/admin/delete_user ，验证403
TC_AUTH_V_003: 未登录用户访问需要登录的页面，验证跳转登录
TC_AUTH_V_004: 免费用户访问VIP功能，验证提示升级
```

**历史案例**: URL参数越权、隐藏页面越权导致数据泄露

## 二、业务风险模式

### 2.1 支付流程风险

#### 金额篡改
```
风险点:
✅ 前端传递金额到后端
✅ 优惠券金额计算在前端
✅ 商品价格从前端传递

测试用例:
TC_PAY_001: 使用代理工具修改金额参数，验证后端校验
TC_PAY_002: 修改商品数量为负数，验证拦截
TC_PAY_003: 使用过期的优惠券，验证失效
TC_PAY_004: 叠加多个优惠券导致负价格，验证拦截
```

#### 重复支付
```
风险点:
✅ 快速点击支付按钮
✅ 网络抖动导致重复请求
✅ 浏览器后退重新提交

测试用例:
TC_PAY_011: 快速点击支付按钮10次，验证只扣款1次
TC_PAY_012: 支付中刷新页面，验证不会重复扣款
TC_PAY_013: 支付成功后点击浏览器后退，验证不能重新支付
TC_PAY_014: 模拟网络延迟，点击2次支付，验证幂等性
```

#### 支付回调伪造
```
风险点:
✅ 支付回调没有签名验证
✅ 回调URL可被外部访问
✅ 重放攻击

测试用例:
TC_PAY_021: 伪造支付成功回调，验证是否被拦截
TC_PAY_022: 重放历史支付回调，验证是否被识别
TC_PAY_023: 篡改回调中的金额，验证签名校验
```

**历史案例**: 前端金额篡改、重复支付导致资金损失

---

### 2.2 库存超卖风险

#### 并发购买（简化版）⭐
```
风险点:
✅ 快速重复点击购买按钮
✅ 购物车数量大于库存

测试用例（简化）:
TC_INV_001: 快速点击购买按钮5次，验证只生成1个订单
TC_INV_002: 购物车数量大于库存，验证限制提示

❌ 不推荐测试（这是性能测试/压力测试）:
   - 100人并发购买
   - 1000人秒杀场景
   - 复杂的分布式锁验证
```

**理由**：功能测试只测基础防重，大规模并发是性能测试的范畴。

---

### 2.3 验证码风险

#### 暴力破解（简化版）⭐
```
风险点:
✅ 验证码可以多次尝试
✅ 验证码可以重复使用

测试用例（简化）:
TC_CAPTCHA_001: 连续输入错误验证码5次，验证是否限制
TC_CAPTCHA_002: 使用同一验证码提交2次，验证第2次失败
TC_CAPTCHA_003: 验证码60秒后使用，验证失效

❌ 不推荐测试:
   - 100次暴力尝试
   - 脚本枚举验证码
   - 复杂的频控算法验证
```

**理由**：基础防护测试足够，复杂的暴力破解防护由安全团队负责。

## 三、数据风险模式

### 3.1 数据泄露风险

#### 敏感信息暴露
```
风险点:
✅ 接口返回过多信息（密码hash、手机号全显示）
✅ 错误信息泄露系统信息
✅ 日志记录敏感数据
✅ 前端代码包含密钥

测试用例:
TC_DATA_001: 查看接口返回，验证是否包含密码字段
TC_DATA_002: 查看用户列表，验证手机号是否脱敏
TC_DATA_003: 触发500错误，验证错误信息不包含SQL语句
TC_DATA_004: 查看前端代码，验证不包含API密钥
```

---

### 3.2 数据篡改风险

#### 前端数据可信度
```
风险点:
✅ 前端传递的数据直接入库
✅ 重要字段（价格、权限）从前端传递
✅ 没有后端二次校验

测试用例:
TC_DATA_021: 修改商品价格参数，验证后端重新计算
TC_DATA_022: 修改用户角色参数，验证后端拒绝
TC_DATA_023: 修改订单状态参数，验证后端校验权限
```

### 4.2 DoS攻击风险

#### 资源耗尽（简化版）⭐
```
风险场景（只测产品明确的上限）:
✅ 上传文件大小限制（如产品限制10MB，则测试10MB）
✅ 批量操作数量限制（如产品限制100条，则测试100条）

TC_DOS_001: 上传达到上限的文件，验证是否允许
TC_DOS_002: 批量操作达到上限数量，验证是否限制

❌ 不推荐测试（极端场景）:
   - 100GB文件上传
   - 一次删除100万条
   - ReDoS正则攻击
   - 递归调用深度
```

**理由**：只测产品文档明确的限制，不测理论极限。

## 六、风险优先级评估模型

### STRIDE风险评分

| 风险类型 | 影响程度(1-10) | 发生概率(1-10) | 风险评分 | 优先级 |
|---------|---------------|---------------|---------|--------|
| SQL注入 | 10 | 7 | 70 | P0 |
| XSS攻击 | 9 | 8 | 72 | P0 |
| 金额篡改 | 10 | 6 | 60 | P0 |
| 横向越权 | 9 | 7 | 63 | P0 |
| CSRF | 7 | 5 | 35 | P1 |
| 库存超卖 | 8 | 4 | 32 | P1 |
| 慢查询 | 5 | 6 | 30 | P1 |
| 样式错乱 | 2 | 3 | 6 | P3 |

**风险评分 = 影响程度 × 发生概率**
- 60+ → P0 (必须测试)
- 30-59 → P1 (重点测试)
- 10-29 → P2 (选择性测试)
- <10 → P3 (低优先级)

## 七、风险识别自动化规则

### 规则引擎

```python
def auto_detect_risks(figma_design, feature_type):
    risks = []
    
    # 规则1: 检测表单 → SQL注入风险
    if has_form_input(figma_design):
        risks.append({
            'type': 'SQL注入',
            'level': 'HIGH',
            'test_cases': generate_sql_injection_tests()
        })
    
    # 规则2: 检测用户内容展示 → XSS风险
    if has_user_content_display(figma_design):
        risks.append({
            'type': 'XSS攻击',
            'level': 'HIGH',
            'test_cases': generate_xss_tests()
        })
    
    # 规则3: 检测支付功能 → 金额篡改风险
    if feature_type == 'payment':
        risks.append({
            'type': '金额篡改',
            'level': 'HIGH',
            'test_cases': generate_payment_security_tests()
        })
    
    # 规则4: 检测用户数据访问 → 越权风险
    if has_user_data_access(figma_design):
        risks.append({
            'type': '横向越权',
            'level': 'HIGH',
            'test_cases': generate_authorization_tests()
        })
    
    return risks
```

## 总结：风险识别的黄金法则（实用性优先版）⭐

1. **看到钱就想安全** - 涉及支付/金额必须重点测试
2. **看到输入就想注入** - 但只测1-2个典型payload
3. **看到展示就想XSS** - 但只测基础<script>标签
4. **看到权限就想越权** - 重点测横向越权（改用户ID）
5. **看到并发就想超卖** - 但只测重复点击，不测1000人并发
6. **历史会重演** - 类似功能的历史Bug必须回归

**新增原则**：
7. **问自己：用户会这样做吗？** - 如果不会，别测
8. **简化安全测试** - 典型场景足够，不追求完美
9. **排除极端场景** - 100GB文件、10000层嵌套等
10. **控制用例数量** - 小≤30条，中≤60条，大≤100条

**记住**: 风险识别要**实用优先**，详见 `practical_test_rules.md`。
