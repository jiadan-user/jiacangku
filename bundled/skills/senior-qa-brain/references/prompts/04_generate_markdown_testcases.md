# Prompt: 生成Markdown格式测试用例

## 目标
从测试分析报告生成结构化的Markdown格式测试用例文档。

---

## 输入信息

1. **测试分析报告** - 已确认的功能理解、流程、字段、风险点
2. **用户反馈** - 对待确认问题的回答
3. **项目名称** - 通用参数，不硬编码
4. **PRD 差距分析章节**（可选）- 若报告中包含，将缺失/冲突点纳入用例生成范围
5. **业务规则库依据**（由 QA Agent instruction 指定）- 只读取指定的 `bundled/knowledge_base/业务规则库` 文件或目录，不自行扫描历史文本用例、业务知识图谱或产品全景

## 用例编写原则

### 1. 实用性优先（最重要）⭐
**问自己：用户会这样做吗？如果不会，别测！**

- ✅ 测试真实用户场景
- ✅ 测试核心业务价值
- ❌ 不测极端理论场景（如10000字符输入）
- ❌ 不测第三方依赖完整流程（如微信登录的所有分支）
- ❌ 不测无法控制的内容（如第三方网站链接）

### 2. 标题清晰
- ✅ "用户正常登录"
- ✅ "用户名为空登录"
- ❌ "测试登录" (太模糊)

### 3. 前置条件具体
- ✅ "用户已注册,账号状态正常"
- ❌ "系统准备好" (太模糊)
- ✅ "访客身份；打开 https://ae.58v5.cn/en/city-abu-dhabi/cate-car/?iconSource=car；确认页面标题含 Cars 且筛选栏可见"
- ✅ "已登录卖家账号 dc_seller_ae；访问 /biz/en/wallet/home；确认 Wallet balance 区块显示"
- ❌ "已进入列表页" (缺少角色、入口URL/路径、准备动作、就绪验证点)

### 3.1 UI自动化前置条件必须可执行
每条 `UI自动化=✅` 的用例，前置条件必须同时说明：
- 角色/登录态
- 入口 URL 或导航路径
- 账号/测试数据（无需登录时写明"访客/无需登录"）
- 准备动作
- 就绪验证点

禁止只写："系统准备好"、"数据已准备好"、"账号正常"、"已进入页面"。

### 4. 执行步骤可操作
- ✅ "点击'登录'按钮"
- ❌ "进行登录操作" (太抽象)

### 5. 预期结果可验证
- ✅ "显示'登录成功'提示"
- ❌ "系统正常" (无法验证)

### 6. 优先级合理
- **P0**: 核心功能,阻塞上线（占比20-30%）
- **P1**: 重要功能,严重影响体验（占比40-50%）
- **P2**: 一般功能,轻微影响（占比20-30%）
- **P3**: 优化项,不影响主流程（占比<10%）

### 7. UI自动化判断准确
- **✅ 可自动化**: 纯Web UI操作 + 有明确验证点 + 无第三方授权/支付/验证码
- **❌ 不可自动化**: 需人工判断视觉效果 / 第三方OAuth / 真实支付 / 人机验证
- **注意**: 只需要简单标记"✅ 可自动化"或"❌ 不可自动化"，不需要详细说明自动化方式

## 用例数量建议（基于80/20原则）⭐

| 项目规模 | 推荐用例数 | 预估生成时间 | 说明 |
|---------|----------|------------|------|
| 小型功能（1-3页面） | 20-30条 | 5-8分钟 | 核心流程+关键异常 |
| 中型功能（4-8页面） | 40-60条 | 10-15分钟 | 核心流程+常见场景+关键异常 |
| 大型功能（9+页面） | 80-100条 | 20-30分钟 | 完整覆盖但排除极端场景 |

**重要原则**: 
- ✅ **质量 > 数量**：30条精准用例 > 100条冗余用例
- ✅ **80/20法则**：Top 10-15%的用例可发现75-90%的缺陷
- ✅ **覆盖率目标**：需求覆盖≥95%（不追求100%）
- ❌ **避免过度**：超过100条说明包含了过多极端/不实用场景

**分批策略**: 
- 第一批：核心用例(20-30条，P0/P1优先级)
- 第二批：补充关键异常场景(10-20条)
- 控制总数：小功能≤30条，中等≤60条，大功能≤100条

## UI自动化标记规范 ⚠️ 重要

### 标准格式（必须遵守）

每条用例**必须**包含一行UI自动化标记：

```markdown
**UI自动化**: ✅ 可自动化
```

或

```markdown
**UI自动化**: ❌ 不可自动化
```

### ❌ 禁止格式

**不要**添加额外的"自动化方式"说明行：

```markdown
❌ 错误示例：
**UI自动化**: ✅ 可自动化
**自动化方式**: 数据库操作（设置5分钟后）+ 等待 + 数据库验证或Mock时间

✅ 正确示例：
**UI自动化**: ✅ 可自动化
```

### 判断规则

**✅ 可自动化** - 满足所有条件：
- 纯Web UI操作（点击、输入、选择）
- 有明确的验证点（文本、URL、元素状态）
- 无第三方授权（微信/Google登录）
- 无真实支付流程
- 无人工验证码/滑块

**❌ 不可自动化** - 存在任一情况：
- 需人工判断视觉效果
- 第三方OAuth授权
- 真实支付验证
- 人机验证
- 主观感受判断

## 生成后自检

### 实用性检查（最重要）⭐
- [ ] 用例总数是否符合规范？（小≤30，中≤60，大≤100）
- [ ] 是否排除了极端场景？（如10000字符、100GB文件）
- [ ] 是否排除了第三方依赖完整测试？（如微信登录全流程）
- [ ] 安全测试是否简化？（SQL注入1-2个payload，不是20个）
- [ ] 边界值是否只测明显边界？（最小值、最大值，不测中间值）
- [ ] 并发测试是否简化？（重复点击，不是1000人并发）

### 质量检查
- [ ] 每条用例都有前置条件
- [ ] 每条用例都有执行步骤(至少1步)
- [ ] 每条用例都有预期结果(至少1条)
- [ ] 每条用例都有优先级
- [ ] 用例编号连续无遗漏

### 覆盖度检查（不追求100%）
- [ ] 核心流程覆盖 ≥95%
- [ ] 关键异常场景覆盖 ≥80%（不是所有异常）
- [ ] 基础安全测试覆盖（简化版）
- [ ] 明显边界值覆盖（不是所有边界）

### UI自动化标记检查
- [ ] 每条用例都有UI自动化标记
- [ ] 自动化判断符合Playwright能力范围
- [ ] 统计表格包含自动化率数据

## Token消耗预估（实用性优先）

- **小型功能** (20-30条用例): 约15K-20K tokens
- **中型功能** (40-60条用例): 约30K-50K tokens
- **大型功能** (80-100条用例): 约70K-100K tokens

**节省建议**:
- 遵循80/20原则，控制用例数量
- 优先生成核心用例（P0/P1）
- 排除极端场景和第三方依赖测试
- 简化安全测试和边界值测试
- 分批生成避免一次性消耗
- 使用快速版分析报告减少输入token
