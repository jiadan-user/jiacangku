# 知识库架构模式

## 推荐架构（新版）

### 产品全景
**定位**：顶层产品设计和架构  
**典型内容**：产品架构图、功能模块清单、技术架构、用户角色权限体系、核心业务流程总览

### 业务知识图谱
**定位**：业务全貌和流程上下文  
**典型内容**：
- **业务全景文档**：完整的业务流程、页面拓扑、观测点、数据流转
- **业务流程文档**：详细的流程步骤、判断分支、异常处理
- **按业务域组织**：每个业务域一个子目录（如"房产业务域"、"招聘业务域"）

### 业务规则库
**定位**：具体可执行的业务规则  
**典型内容**：
- **模块规则**：各模块的详细业务规则（扁平化组织，无"模块规则"中间层）
- **通用规则**：表单校验、错误码、权限控制、数据格式、AI能力等
- **站点差异**：多站点的规则差异（或合并到模块规则中）

**目录结构示例**：
```
产品知识库/
├── 产品全景/
│   ├── 产品架构图.md
│   ├── 功能模块清单.md

│
├── 业务知识图谱/
```

## 架构适配策略

### 自动扫描模式

当知识库已存在时，通过扫描目录自动推断架构：

```bash
# 扫描目录结构
find <知识库路径> -type d -maxdepth 3

# 识别层级
- 包含"架构"、"流程" → 产品架构层
- 包含"规则"、"校验" → 业务规则层
- 包含"测试"、"场景"、"缺陷" → 测试知识层

# 识别模块
- 用户、账户、登录 → 用户模块
- 商品、发布、搜索 → 商品模块
- 订单、交易、支付 → 交易/支付模块
```

### 动态扩展

发现新模块时：

1. **询问用户**："发现新模块'XX模块'，是否需要扩展知识库结构？"

2. **创建标准结构**：
   ```bash
   mkdir -p "业务规则层/模块规则/XX模块"
   ```

3. **参考已有模块**：
   - 查看其他模块的文件命名
   - 创建类似的标准文件（如：XX规则.md）

### 灵活映射

**原则**：架构是指导，不是约束

**处理方式**：
- 内容适合现有分类 → 放入对应位置
- 内容不适合现有分类 → 建议创建新分类
- 跨模块内容 → 放在通用规则/或创建独立文件

**示例**：
```
内容："全局搜索功能规则"
分析：涉及商品搜索、用户搜索、订单搜索
决策：放在 通用规则/搜索规则.md（而非某个模块下）
```

## 常见问题

### Q1: 内容应该放在哪一层？

**判断标准**：
- 描述"是什么" → 产品架构层
- 描述"怎么做" → 业务规则层
- 描述"如何测" → 测试知识层

### Q2: 通用规则 vs 模块规则？

**通用规则**：适用于多个模块的规则
- 示例：表单校验、错误码、权限控制

**模块规则**：仅适用于特定模块的规则
- 示例：登录规则、商品发布规则

### Q3: 站点差异如何组织？

**方式 1**：独立文件
```
站点差异/
├── US站特有规则.md
├── AE站特有规则.md
└── BR站特有规则.md
```

**方式 2**：在通用规则中标注
```markdown
## 货币显示规则

| 站点 | 格式 | 示例 |
|------|------|------|
| US   | $1234.56 | 无千分位 |
| EU   | 1.234,56€ | 有千分位 |
| CN   | ¥1,234.56 | 有千分位 |
```

选择标准：差异大用方式1，差异小用方式2

### Q4: 如何处理跨层级内容？

**示例**：用户登录

- **产品架构层**：登录流程图（宏观流程）
- **业务规则层**：登录校验规则（具体规则）
- **测试知识层**：登录测试场景（测试方法）

**处理**：三处都保留，添加交叉引用

```markdown
# 登录规则（业务规则层）

参考：
- 流程图：[用户登录流程](../../产品架构层/业务流程图/用户登录流程.md)
- 测试场景：[登录测试场景](../../测试知识层/测试场景库/正向场景清单.md#登录场景)
```
