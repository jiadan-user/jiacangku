# 核心执行原则与心智模型 (Agent Execution Guide)

> 本文档帮助你（AI Agent）理解为什么我们需要严格遵守录制流程，以及如何避免常见的生成失败。

---

## 🔍 为什么不要“跳跃”或“猜测”？

作为 AI，你具备强大的推理和代码生成能力。当你看到相似的测试用例（如 TC001 和 TC002）时，你可能会本能地想：“我可以直接根据 TC001 生成 TC002，不需要真的去调用浏览器”。

**请克制这种“优化”指令的冲动！**

在现代 Web 自动化测试中，**AI 的“聪明猜测”往往会导致运行时的脆弱性**：
1. **动态 DOM 结构**：同一个表单的不同输入可能会触发完全不同的 DOM 变化（如防抖请求、动态推荐列表、异步错误提示）。
2. **隐藏状态**：页面上的 `text="XXX"` 可能会命中多个元素（其中包括不可见的缓存组件），单凭推理想象无法确定哪个才是可交互的。
3. **隐性依赖**：操作的等待时间（timeout）、接口响应速度，只能通过真实交互来感知。

因此，**“笨拙地按步录制”远胜于“聪明地凭空生成”**。

---

## ✅ 你的最佳实践工作流

为了产出 100% 可运行的自动化代码，请将自己视为一个**严格的浏览器测试员**，遵循以下心智模型：

### 1. 视“证明存档”为你的唯一真理
不要试图记住所有的选择器，也不要凭空捏造。你在阶段 3（代码生成）时，唯一的数据来源只能是你在阶段 2 真实执行的 CLI 命令返回结果（`### Ran Playwright code`）。

### 2. 把验证步骤视为一等公民
很多时候，你可能只录制了“点击”和“输入”，却忘了录制“断言”。
- **错误**：自己想象验证逻辑，如 `expect(page.locator('.success')).to_be_visible()`。
- **正确**：在浏览器里用 `browser_wait_for` 等待成功提示，用 `browser_take_screenshot` 保存状态，把这些作为验证代码的依据。

### 3. 主动进行状态汇报，防止自己迷失
在处理长长的一串测试用例时，由于上下文窗口的限制，你可能会迷失当前进度。
- 每次回复结尾，请务必输出 `> 当前状态：...`。
- 如果用户一次性给了 20 个用例，主动要求分批（如每次 5 个），这能极大地保护你的短期记忆。

## 🚨 当你遇到诱惑时，请停下来

- **诱惑 1**：看到 TC003 是异常流程，你想直接复制 TC001 的代码改改报错信息。
  👉 **抵抗**：异常流程的验证点完全不同，必须重新通过 `browser_navigate` 和真实操作来获取页面报错的选择器。
- **诱惑 2**：你想一次性输出所有用例的执行计划。
  👉 **抵抗**：描述计划毫无意义，我们需要的是你通过 CLI 真实调用的数据。

**核心总结**：不要试图跳过录制直接写代码，不要猜测选择器。你的价值在于通过真实的 CLI 调用连接起“自然语言用例”与“高可用自动化代码”。
